# Assembler

Assembler turns a natural-language request into a **specification**, an inspectable
**blueprint**, and a real, working web project — then installs, typechecks, tests
and production-builds that project before publishing it.

It is deterministic: the same request and the same knowledge files produce the same
files with the same hashes. Nothing is generated by a language model at build time.

```bash
mkdir my-blog && cd my-blog
assembler
```

Type a request into the prompt, watch it run through the pipeline, and get the
project in the directory you were standing in.

## Prerequisites

- **Node.js ≥ 18.18** (`node --version`)
- **pnpm 9** (`corepack enable`, or `npm i -g pnpm@9`) — workspace installs use pnpm
- **npm** — only needed for `npm link` (global installation)

## Installation

```bash
git clone <repo> assembler && cd assembler
pnpm install        # installs workspace dependencies
pnpm run build      # tsc -b, produces apps/cli/dist and packages/*/dist
npm link            # makes `assembler` available on PATH
```

`npm link` only symlinks this checkout; it does **not** install dependencies, so
`pnpm install` must come first. If you skip `npm link`, everything below still
works through `node /path/to/assembler/bin/assembler.js`.

Missing steps fail with a specific message instead of a module error, e.g. running
`assembler` without `pnpm run build` tells you which command to run.

## Launching from any directory

```bash
mkdir my-blog
cd my-blog
assembler
```

The interface shows the absolute workspace path at the top and builds into it:

```
ASSEMBLER 0.1.0                          ● [1/6] Interpreting request…
Workspace: /home/you/my-blog
────────────────────────────────────────────────────────────────────────
› Build a complete responsive personal blog using React, TypeScript, and Vite,
  with search, categories, individual post pages, and sample posts
• [1/6] Interpreting request…
• [2/6] Creating project specification…
• [3/6] Checking environment and dependencies…
• [4/6] Generating blueprint…
• [5/6] Assembling project…
• [6/6] Validating and building…
✓ Project generated successfully.
> ▏
────────────────────────────────────────────────────────────────────────
enter submit · /help commands · /quit exit · ctrl+c interrupt
```

Each phase label wraps a real awaited operation; the last phase only reports
success after `install`, `typecheck`, `test` and `build` have all finished
successfully. Step output (`install: ok (21.8s) — pnpm install …`) is printed as
it happens.

### Slash commands

| Command | What it does |
| --- | --- |
| `/help` | list the commands above (only ones that actually work) |
| `/workspace` | show the absolute workspace path and what is in it |
| `/plan [request]` | interpret + plan and report files and conflicts, writing nothing |
| `/inspect` | verify the project against its recorded manifest |
| `/doctor` | environment diagnostics: runtimes, package managers, capabilities |
| `/history` | assemblies recorded in this workspace |
| `/analyze` | read-only inventory of existing code |
| `/clear` | clear the log |
| `/quit` | exit |

Anything else starting with `/` produces "Unknown command" plus a pointer to
`/help`. Up/down walks your request history, PageUp/PageDown scroll the log, Escape
clears the prompt, Ctrl+L redraws, Ctrl+C cancels a running build (press again to
exit).

## Choosing a workspace

- Default: `process.cwd()` — the directory you launched from.
- Explicit: `assembler --workspace /path/to/project` (works with `--prompt` too).
- Assets (templates, `knowledge/`, `libraries/`) always come from the Assembler
  installation; they are never looked up in, or written to, your project.
- State (the SQLite database and backups) lives in `<workspace>/.assembler/`.

## Safety when files already exist

Before writing anything, Assembler inspects the directory and reports
`new / unchanged / conflicting / unrelated` counts. Unrelated files are **never**
touched: only paths from the plan are written, and everything else is left as it
is.

- A planned file that already exists with *different* content stops the build and
  asks for confirmation (`yes` / `no`). Declining writes nothing.
- `assembler.spec.json`, `assembler.manifest.json` and `assembler.report.json` are
  Assembler's own metadata and are refreshed silently.
- In non-interactive mode nothing waits for a keypress: the build stops, explains
  `Re-run with --yes`, and exits `2`.
- Nothing is ever deleted. `--overwrite replace|backup` (used by `build --target`)
  is not used by the in-place flow at all.
- Path traversal is enforced centrally: a planned path or a target outside the
  authorized workspace is rejected (`OVERWRITE_DENIED`).

```bash
assembler --prompt "..." --yes     # accept overwriting the conflicting files
assembler --prompt "..." --workspace /path/to/dir
```

## Non-interactive use (scripts, CI)

```bash
assembler --prompt "Create a React dashboard called Demo" --yes
assembler "Create a React dashboard called Demo" --no-install --no-build
assembler --non-interactive --prompt "..."     # fails unless --prompt is given
```

Exit codes: `0` success, `1` the operation ran and failed, `2` usage /
specification / plan blockers / conflicts, `3` a required capability is missing,
`4` not implemented. Invoking `assembler` with no arguments on a pipe explains
this and exits `2` instead of emitting escape codes.

## Commands

| Command | Purpose |
| --- | --- |
| `interpret "<request>" [--out file]` | Requirement → validated specification (with provenance and clarifications) |
| `plan <spec.json> [--out blueprint.json]` | Specification → blueprint: files, components, commands, capability checks, blockers |
| `build <spec.json> [--target dir] [--overwrite deny\|backup\|replace]` | Plan → stage → verify manifest → install → typecheck → test → build → publish |
| `inspect <dir>` | Re-verify a generated project against its recorded manifest |
| `test <dir>` | Run an existing project's test script with the detected package manager |
| `analyze [<dir>]` | Read-only inventory: targets, dependencies, imports, tests, unresolved imports |
| `debug [<dir>]` | Analysis + environment status + recorded diagnostics |
| `doctor` | Detect runtimes, package managers, SDKs and report capability status |
| `registry <list\|search\|inspect\|add\|verify\|deprecate>` | Verified component registry (SQLite index over `libraries/`) |
| `history [--limit n]` | Recorded assemblies and outcomes |
| `init` | Create the workspace config and data directory |
| `adopt`, `repair`, `docs` | **Not implemented** — they report this and exit 4 |

`--json` is available on every command and is the only machine-readable contract.

## What it actually produces

For `Create a glassmorphism React dashboard …`, `plan` produces a 47-file blueprint
for a Vite + React + TypeScript app:

- a Vite/React/TypeScript project pinned by `knowledge/versions.json`
- routing via `react-router-dom`, an `AuthProvider`, API client, validation helpers,
  `useAsync` hook, and shared `Button`/`Card`/`TextField`/`PageHeader`/`States`
  components, each with a test
- design tokens generated from the request (`glassmorphism`, dark theme, blur,
  contrast-checked primary colour)
- pages generated from the request (`/`, `/dashboard`, `/records`), each with a
  route, a layout entry and a test
- `assembler.spec.json` and `assembler.manifest.json` recording the request, the
  plan hash and every file's SHA-256 and provenance

## How it works

```
request ──► requirement-parser ──► project-spec ──► project-planner ──► project-assembler
                   │                    │                 │                    │
              ledger +          semantic validation   template-engine      staged write,
              clarifications    + contradictions      + component-registry manifest check,
                                                      + knowledge pins     install/test/build
```

- `packages/core` — workspace, config, path safety, atomic filesystem, process
  runner with timeouts, SQLite migrations, structured logging, HTTP.
- `packages/environment-manager` — probes Node, package managers, network, SDKs;
  reports capability status instead of assuming them.
- `packages/project-spec` — the specification schema and semantic validation.
- `packages/requirement-parser` — deterministic extraction of applications, pages,
  design, stack and testing needs, with a requirement ledger and explicit
  contradictions/unsupported entries.
- `packages/template-engine` — deterministic rendering (`{{var}}`, conditionals,
  loops) with no user-controlled code execution.
- `packages/component-registry` — component metadata in SQLite, sources on disk,
  lifecycle states and structural verification.
- `packages/project-planner` — blueprint, generated-file manifest, import graph,
  cycle/missing-import analysis, blocker detection.
- `packages/project-assembler` — staging, manifest reconciliation, dependency
  installation, verification commands, publication and history.
- `packages/diagnostic-engine` — normalises process failures into typed diagnostics.
- `apps/cli` — thin adapters over the services above, plus the interactive
  interface in `apps/cli/src/tui/`.

Assets live outside the packages so they can be inspected and versioned:
`templates/react-web`, `libraries/web/*`, and `knowledge/versions.json` +
`knowledge/design.json`.

### The interactive interface

`apps/cli/src/tui/` is split so rendering never touches generation logic:

- `session.ts` — the controller: input handling, slash commands, the six pipeline
  phases, conflict confirmation. It calls the same interpreter, planner and
  assembler the commands do.
- `screen.ts` — full-screen ANSI renderer (alternate screen, header, log, prompt,
  status bar), width-aware, resize-tolerant.
- `plain.ts` — line renderer for `--prompt` (the same log, no escape codes).
- `keys.ts` — raw-mode key decoding, including bracketed paste.
- `index.ts` — terminal lifecycle: raw mode, SIGINT/SIGWINCH, guaranteed cleanup.

It has **no dependencies**: no native modules, no node-pty, nothing to compile —
which is what makes it work on Android terminals (Termux/TermDeb/TermBox) as well
as Linux.

## Tests

```bash
pnpm run typecheck   # tsc -b, all packages
pnpm test            # unit + integration + e2e (including the linked executable)
pnpm run test:unit
pnpm run test:integration
pnpm run test:e2e
```

`tests/e2e/linked.test.ts` runs `npm link` and then drives `assembler` from a
temporary directory outside the repository, including a full build and the
generated project's own `typecheck`/`test` runs. It unlinks afterwards.

What is covered, and what is not, is recorded in [docs/verification.md](docs/verification.md).

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `the build is missing` | run `pnpm install && pnpm run build` in the checkout |
| `runtime dependencies are not installed` | run `pnpm install` |
| `command not found: assembler` | run `npm link`, or call `node <checkout>/bin/assembler.js` |
| `The interactive interface needs a terminal (a TTY)` | you are in a pipe/script — use `--prompt "<request>"` |
| Exit `2` with `Re-run with --yes` | existing files conflict; review them, then add `--yes` |
| Exit `3` | a required capability is missing — run `assembler doctor` |
| Raw escape sequences on screen | the terminal does not support the alternate screen; use `--prompt` |
| Build failed but the directory looks untouched | by design: the project is staged, verified and only then published |

## Limitations

Assembler is honest about what it cannot do:

- **One target.** Only `react-web` (Vite + React + TypeScript) can be generated.
  Requests for backends, mobile, desktop or other frameworks are reported as
  blockers (`TARGET_NOT_IMPLEMENTED`), not approximated.
- **No modification of existing projects.** `adopt` is analysis-only and `repair`
  is unimplemented; neither modifies files. The interactive flow writes *new*
  projects into the workspace and never edits pre-existing ones beyond the files
  it generates (after confirmation).
- **Registry verification is structural.** `registry verify` checks manifest shape,
  file hashes, exports and dependency dependencies statically. It does not execute
  component tests, and the registry says so (`claimsTested` / verification level).
- **Heuristic interpretation.** The requirement parser uses a lexicon, not an LLM.
  It records every fact's provenance (`requested`, `derived`, `default`,
  `assumption`) and asks for clarification rather than inventing intent. Extra
  asks (e.g. full-text search) are reported as unmatched rather than half-built.
- **No documentation index, no network knowledge refresh.** Versions are pinned in
  `knowledge/versions.json`; updating them is a manual, reviewable commit.
- **Terminal coverage.** Ctrl+C, resize and cleanup are exercised through the
  session/renderer and a pseudo-terminal; exotic terminals (no alternate screen,
  no bracketed paste) degrade to a plain, smaller layout.
